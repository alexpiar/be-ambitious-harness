## 1. Цель и результат
Цель: построить модель, которая предсказывает отток пользователей по их событиям, и определить, какие признаки важнее всего для этого предсказания.
Что должно стать возможным: в заданный момент жизни пользователя заранее отличать тех, кто отменит подписку, от остальных, с известной и подтверждённой на отложенных данных точностью относительно простых правил; опираться на проверенный список признаков (без утечки, устойчивый), понимая, что он предсказательный, а не причинный.
Схема: условная. Планка: всегда базовая (модель на 14-й день после регистрации плюс важность признаков с интервалами); после пройденной проверки и при заданном пределе затрат добавляется амбициозная: цель-исследование «сигнал раньше и точнее за счёт истории: риск отмены в ближайшие 30 суток на любую дату по всей истории пользователя до неё»; гипотеза (не критерий): на срезах по датам у holdout-пользователей ROC AUC модели с историей выше, чем у модели D = 14 на тех же срезах, нижняя граница 95 % ДИ разности > 0.

## 2. Обязательные требования и границы
Исходная задача дословно: «Вот события пользователей за год. Построй модель, которая предсказывает отток, и скажи, какие признаки важнее всего»
— Материал: «события пользователей за год» (раздел 3). Интернет для работы не нужен.
— Для проверки без автора сдаются сохранённая модель и score.py <events.csv> <points.csv> <out.csv> (блок «Для воркера» сценария data-analysis).
Противоречия: нет. «Отток» и «важнее» не определены; рабочие определения — раздел 5, допущения.

## 3. Материалы и доступы
Необходимые:
— CSV: `gen_events.py events_2025.csv 2026 6000 --profile t2pass` (sha256 `683bfcf7…6fb470`), 408 992 события 6000 пользователей за 2025 год; колонки ts, user_id, event, value, plan, device, country, channel.
— Python 3.10 с numpy, pandas, scikit-learn; память ограничена: n_jobs ≤ 2, без тяжёлых переборов.
Необязательные: словарь полей; сведения об изменениях сбора; бизнес-определение оттока.
Если необходимых нет — запросить у меня до начала работы.

## 4. Входная проверка
Действие и материалы: выполняется после этапа 0 раздела 5 (качество данных проверено, holdout отложен), только на dev-части, CSV и Python из раздела 3.
— Срез D = 7: T = ts(signup) + 7 суток.
— Популяция: пользователи без cancel до T. Метка: cancel в интервале (T, T + 60 суток].
— Две логистические регрессии со стандартизацией, seed 42: (А) только статические признаки; (Б) статические плюс поведенческие (наборы из раздела 5).
— Оценка: 5-кратная стратифицированная CV по пользователям, out-of-fold предсказания. 95% бутстрэп-ДИ (1000 повторов по пользователям) для ROC AUC(Б) и для разности ROC AUC(Б) − ROC AUC(А) на одних и тех же OOF-предсказаниях.
Наблюдаемый результат:
— ROC AUC(Б) и его 95% ДИ;
— разность ROC AUC(Б) − ROC AUC(А) и её 95% ДИ;
— размер популяции среза и число положительных меток в ней.
Критерий прохождения (зафиксирован, пересмотру не подлежит): ROC AUC(Б) ≥ 0.65 и нижняя граница 95% ДИ разности ROC AUC(Б) − ROC AUC(А) > 0. Обоснование: 0.65 — нижний уровень ранжирования, пригодного для отбора на удержание; положительная разность означает, что поведение первой недели добавляет сигнал сверх известного при регистрации. Если в dev-популяции среза меньше 100 положительных меток, критерий неприменим.
Предел затрат: 40 минут работы воркера, один скрипт, только dev-часть; holdout не открывается.
Пройдена → если предел затрат на амбициозную ветку задан, выполняются этапы 2 и 3. Предел: 2 часа. Если предел не задан, выполняется только этап 2, а в отчёте даётся оценка затрат и ожидаемого выигрыша этапа 3 для моего решения.
Не пройдена → выполняется только этап 2; в отчёте — полученные значения и почему проверка не пройдена.
Данных недостаточно (предел затрат исчерпан, результат ненаблюдаем или критерий неприменим) → выполняется только этап 2; в отчёте — что осталось неизвестным и что нужно, чтобы это узнать.
Исход записывается в журнал блоком GATE по форме из core/gate.md до первого действия этапа 3.
Работа амбициозной ветки начинается после зафиксированного исхода.

## 5. Подход и этапы
Рабочие определения (допущения; изменить их может только человек): отток — событие cancel; T = ts(signup) + D суток, основной срез D = 14; популяция — без cancel до T; метка — cancel в (T, T + 60 суток]; признаки — только события с ts(signup) ≤ ts ≤ T, кроме cancel и exit_survey; статика — plan, device, country, channel (one-hot); поведение — раздел 5 промпта L2-A 21.10 (число и value сессий, активные дни, функции по видам, payment и payment_failed, support_ticket, был ли plan_downgrade, дней с последнего события, дней до первой сессии); «важнее» — перестановочная важность на holdout, не причинная.
Этап 0 — общий: 0.2 holdout первым действием (20 % пользователей, страта — месяц регистрации, seed 42; список id и SHA-256 — в журнал); 0.1 качество данных на dev; 0.3 один скрипт, seed 42.
Этап 1 — входная проверка по разделу 4.
Этап 2 — базовая ветка при любом исходе: D = 14; ЛР и HistGradientBoosting, небольшая сетка, выбор только по CV на dev (при разнице ≤ 0.005 — ЛР: проще и сохраняется в JSON); бейзлайны: доля базового уровня, ЛР на статике, правило «меньше session_start — выше риск»; одна оценка на holdout: ROC AUC, PR AUC, доля уходящих в топ-20 % и лифт с 95 % бутстрэп-ДИ; важность: перестановочная на holdout (30 перестановок) с ДИ, группы |Спирмен| ≥ 0.8, направление, ранги в фолдах dev и сегментах plan и квартал регистрации; сохранённая модель (model.json) и score.py.
Этап 3 — амбициозная ветка, только после «пройдена», в пределе 2 часа: срезы по датам каждые 7 суток с 2025-02-01 по 2025-12-01; популяция — активные на дату (signup ≤ asof, нет cancel с ts ≤ asof); метка — cancel в (asof, asof + 30 суток]; признаки — история до asof (давность, частота и тренд сессий, функции, списания и неуспешные списания, обращения, понижение) плюс статика; ЛР, C ∈ {0.01, 0.1, 1} по 5-кратной CV на dev с фолдами по пользователям; одна оценка на holdout против модели этапа 2 на тех же срезах, ЛР на статике и правила «дней с последней сессии», ДИ бутстрэпом по пользователям; важность как на этапе 2; фактические затраты ветки — в журнал. Если предел исчерпан — остановиться и отчитаться, что успели.
Передаётся: run.py, score.py, model.json (этап 3, его по умолчанию грузит score.py), model_base.json (этап 2), holdout_ids.txt, results.json, журнал, отчёт.

## 6. Критерии приёмки и проверка
Критерии: 1 — определения записаны; признаки только из ts ≤ T; 2 — holdout отложен до признаков, SHA-256 в журнале, на holdout ничего не выбиралось; 3 — для модели D = 14 и трёх бейзлайнов на holdout ROC AUC, PR AUC, лифт топ-20 % с 95 % ДИ; 4 — важность ранжированным списком с ДИ, направлением, устойчивостью, пометкой «неотличим от нуля» и оговоркой о непричинности; 5 — отчёт о качестве данных; 6 — одна команда воспроизводит все числа, расхождение повторного запуска ≤ 0.005.
Численные цели раздела 1 и этапа 3 — гипотезы, а не критерии приёмки.
Независимая проверка: запуск скрипта на своей копии CSV; обрезка событий после T не меняет таблицу признаков (до 1e-9); сверка SHA-256 holdout; скрытый оракул evals/reference/oracle_churn.py на score.py.
Тест на опровержение: тот же пайплайн на перемешанных метках — 95 % ДИ OOF ROC AUC включает 0.5; признак с одиночным ROC AUC > 0.90 проверяется на утечку.
Подгонка под метрику: признаки после T; plan, если он итоговый; выбор модели, порога, D или признаков по holdout; многократная оценка на holdout.
