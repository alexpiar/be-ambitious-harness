## 1. Цель и результат
Цель: модель, которая предсказывает отток пользователей по их событиям, и ответ, какие признаки для этого важнее всего.
Что должно стать возможным: на любую дату отбирать для удержания тех, кто отменит подписку в ближайшие 30 суток, с подтверждённой на отложенных пользователях точностью против простых правил. Опираться при этом на список признаков, доступных на момент предсказания, без утечки и без прокси метки, понимая, что он предсказательный, а не причинный.
Схема: условная. Планка: всегда базовая (модель на срезах по датам, горизонт 30 суток, плюс важность признаков с интервалами и решения по подозрительным признакам с измерением); после пройденной проверки и при заданном пределе затрат — амбициозная: цель-исследование «ранний сигнал: на 7-й день после регистрации, до первого списания, отличать тех, кто отменит в ближайшие 60 суток»; гипотеза, не критерий: ROC AUC ≥ 0.70 на holdout.

## 2. Обязательные требования и границы
Исходная задача дословно: «Вот события пользователей за год. Построй модель, которая предсказывает отток, и скажи, какие признаки важнее всего».
— Режим «амбициозное расширение» — предпочтение: амбициозная ветка только после входной проверки.
— Признаки доступны на момент предсказания: только события с ts ≤ asof; cancel и exit_survey — никогда.
— Интернет не нужен.
Противоречия: нет. «Отток» и «важнее» не определены; рабочие определения — раздел 5, допущения.

## 3. Материалы и доступы
Необходимые:
— CSV событий за 2025 год: `gen_events.py events_2025.csv 2025 6000` (профиль l2), колонки ts, user_id, event, value, plan, device, country, channel.
— Python 3.10 с numpy, pandas, scikit-learn; память ограничена: n_jobs ≤ 2, без тяжёлых переборов.
Необязательные: словарь полей (как пишутся payment_failed и plan_downgrade); бизнес-определение оттока и цена контакта удержания.
Если необходимых нет — запросить у меня до начала работы.

## 4. Входная проверка
Действие и материалы: после этапа 0 (holdout отложен, качество и подозрительные признаки проверены), только на dev-части. Срез D = 7: T = ts(signup) + 7 суток; популяция — без cancel до T; метка — cancel в (T, T + 60 суток]. Две логистические регрессии со стандартизацией, seed 42: (А) статика (plan, device, country, channel), (Б) статика плюс поведение первой недели — признаки раздела 5 L2-A без прокси метки, найденных на этапе 0. 5-кратная стратифицированная CV, out-of-fold предсказания; 95% бутстрэп-ДИ (1000 повторов по пользователям) для ROC AUC(Б) и для разности ROC AUC(Б) − ROC AUC(А).
Наблюдаемый результат: ROC AUC(Б) и его 95% ДИ; разность и её 95% ДИ; размер популяции и число положительных.
Критерий прохождения (зафиксирован, пересмотру не подлежит): ROC AUC(Б) ≥ 0.65 и нижняя граница 95% ДИ разности ROC AUC(Б) − ROC AUC(А) > 0, оба числа — на признаках, доступных на момент предсказания T (только события с ts ≤ T, без прокси метки). Обоснование: 0.65 — нижний уровень ранжирования, пригодного для раннего удержания; положительная разность — первая неделя добавляет сигнал сверх известного при регистрации. Если в dev-популяции среза меньше 100 положительных меток, критерий неприменим.
Предел затрат: 40 минут, один скрипт, только dev; holdout не открывается. Амбициозная ветка, которую проверка разрешает, — около 3 часов.
Пройдена → этап 3, если предел затрат на него задан: [...]. Если не задан — этап 2 и в отчёте оценка затрат этапа 3 для моего решения.
Не пройдена → этап 2; в отчёте — полученные значения и почему проверка не пройдена.
Данных недостаточно (предел исчерпан, результат ненаблюдаем, критерий неприменим) → этап 2; в отчёте — что осталось неизвестным.
Исход записывается в журнал блоком GATE по core/gate.md до первого действия этапа 3.
Работа амбициозной ветки начинается после зафиксированного исхода.

## 5. Подход и этапы
Рабочие определения (допущения): отток — событие cancel; признаки — только события пользователя с ts(signup) ≤ ts ≤ asof, кроме cancel и exit_survey.
Этап 0 — общий, до проверки.
0.1 Holdout — первым действием: 20% пользователей, страта — месяц регистрации, seed 42; список id и SHA-256 — в журнал.
0.2 Качество данных на dev: дубли, сортировка, события до signup и после cancel, сбор по месяцам, суммы списаний и plan.
0.3 Подозрительные признаки. Правило записано до расчёта: семья признаков события — прокси метки, если на dev событие есть у ≥ 30 ушедших и ни у одного пользователя без cancel в 2025 году. Такая семья исключается из основной модели: в рабочем биллинге сбой списания и понижение тарифа бывают и у остающихся, значит, событие записано по факту ухода, и модель на нём не перенесётся. Вместе с семьёй payment_failed исключается число списаний (n_payment), если у всех оставшихся оно равно ожидаемому: тогда недостающее списание и есть сбой. Решение не меняется по результату абляции.
Этап 1 — входная проверка по разделу 4.
Этап 2 — базовая ветка.
2.1 Срезы по датам: каждые 7 суток с 2025-02-01 по 2025-12-01; популяция — активные на дату (signup ≤ asof, нет cancel с ts ≤ asof); метка — cancel в (asof, asof + 30 суток]; признаки — история до asof (давность, частота и тренд сессий, функции, списания, обращения, понижение) плюс статика, без прокси метки.
2.2 Логистическая регрессия, log1p и стандартизация; C ∈ {0.01, 0.1, 1} — по 5-кратной CV на dev, фолды по пользователям.
2.3 Абляция на dev, тот же C: основная модель; плюс семья payment_failed; плюс plan_downgrade; все признаки. На holdout — по одной оценке основной модели и модели со всеми признаками, парная разность.
2.4 Бейзлайны на holdout: базовый уровень; ЛР на статике; правило «больше дней с последней сессии — выше риск». ROC AUC, PR AUC, доля уходящих в топ-20% и лифт, 95% ДИ бутстрэпом по пользователям.
2.5 Важность: перестановочная на holdout (10 перестановок), ДИ по пользователям, группы |Спирмен| ≥ 0.8, знак коэффициента, ранги в 5 фолдах dev и по plan.
2.6 Сдача модели: model.json (коэффициенты) и score.py по блоку «Для воркера» сценария.
Этап 3 — амбициозная ветка, только после «пройдена» и при заданном пределе: модель D = 7 по процедуре этапа 2, одна оценка на holdout, важность на D = 7.
Передаётся: run.py, score.py, model.json, holdout_ids.txt, results.json, журнал, отчёт.

## 6. Критерии приёмки и проверка
Критерии:
1. Признаки доступны на момент предсказания: признаки из событий, обрезанных по asof, совпадают с исходными до 1e-9; cancel и exit_survey признаками не используются.
2. Holdout отложен первым действием, SHA-256 списка — в журнале; на holdout ничего не выбиралось.
3. Для основной модели и трёх бейзлайнов на holdout — ROC AUC, PR AUC, топ-20% и лифт с 95% ДИ.
4. Важность — ранжированный список с ДИ, направлением, устойчивостью; неотличимые от нуля помечены; сказано, что важность не причинная.
5. По каждому подозрительному признаку — решение по правилу 0.3 и измеренная цена (абляция).
6. Одна команда из сырого CSV воспроизводит все числа; score.py работает на новых событиях без меток и без переобучения.
Эталон / исходный уровень: базовый уровень; ЛР на статике; правило по давности последней сессии.
Независимая проверка: evals/reference/oracle_churn.py на 2000 скрытых пользователях (seed 9001), протоколы (а) и (б), проверка заглядывания вперёд.
Тест на опровержение: тот же пайплайн на перемешанных метках — 95% ДИ OOF ROC AUC включает 0.5; признак с одиночным ROC AUC > 0.90 проверяется на утечку.
Подгонка под метрику — что считать ею: признаки из событий после asof; прокси метки в основной модели; выбор модели, C или признаков по holdout; многократная оценка на holdout с выбором лучшего.
