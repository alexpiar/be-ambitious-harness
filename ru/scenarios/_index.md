# Маршрутизация по сценариям

Выбирай по тому, **где лежит результат**, а не по теме. Задача «проанализировать данные, чтобы решить, запускать ли фичу» — это `decision-plan`, данные там средство. Задача «сделать так, чтобы дашборд не врал» — `data-analysis`.

| Сценарий | Результат | Сигналы |
|---|---|---|
| `design-ux.md` | экран, флоу, макет, прототип, дизайн-система, редизайн | «макет», «экран», «прототип», «Figma», «UX», «онбординг», «флоу», «сделай красивее» |
| `data-analysis.md` | вывод из данных, метрика, модель, отчёт по данным | «проанализируй», «почему упало», «churn», «датасет», «таблица», «корреляция», «A/B» |
| `code-engineering.md` | работающий код, фикс, фича, рефакторинг, инфраструктура | «баг», «падает», «реализуй», «API», «тесты», «производительность», «деплой» |
| `writing-research.md` | текст, статья, обзор, документация, доклад, исследование источников | «напиши», «статья», «обзор», «исследуй тему», «документация», «пост», «спич» |
| `decision-plan.md` | решение, план, стратегия, приоритизация, roadmap | «что делать», «стоит ли», «план», «приоритеты», «стратегия», «выбери между» |
| `generic.md` | всё остальное или смесь без явного центра | — |

## Правила

- Один сценарий на задачу. Смесь — тот, где результат; второй сценарий можно подключить одним пунктом в п.2 разбора как «метод из другой дисциплины».
- Сценарий даёт подсказки к пунктам разбора и блок «Для воркера». Ядро разбора — в `agents/planner.md`; сценарий его не заменяет.
- Если задача не ложится ни в один сценарий и `generic.md` явно беднее нужного — это сигнал добавить новый сценарий, а не растягивать существующий.

## Структура каждого сценария

1. Сигналы и типичная исходная постановка
2. Подсказки к пунктам разбора (1–4)
3. Три-четыре типичные ловушки
4. Блок «Для воркера» — передаётся воркеру вместе с промптом
5. Пример двух планок
