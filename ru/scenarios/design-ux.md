# Сценарий: дизайн и UX

Результат — экран, флоу, макет, прототип, компонент, редизайн. Типичная исходная постановка: «сделай экран X», «улучши онбординг», «нарисуй макет по ТЗ».

## Подсказки к разбору

**П.1 — цель и планки.** Экран — средство. Что должен сделать человек по ту сторону экрана, и что мешает ему сейчас? Базовая планка — макет по брифу. Амбициозная — обычно одна из трёх: убрать шаг вместо того, чтобы улучшить его; найти причину отказа на этом шаге по данным, а не по гипотезе; сделать решение, которое переиспользуется в соседних флоу. Амбициозная планка здесь почти всегда цель-исследование: «выяснить, где и почему люди уходят» — а не «поднять конверсию на N%».

**Входная проверка** для дизайна дешёвая и часто доступна: воронка по шагам из аналитики; 3–5 записей сессий; интервью или коридорный тест на текущей версии; эвристический аудит против списка. Критерий прохождения — наблюдаемый: «в ≥3 из 5 сессий человек останавливается на поле X».

**П.2 — улучшения.** Предположение, которое стоит проверить по первичным данным: что проблема именно в интерфейсе, а не в предложении, цене, доверии или входящем трафике. Дисциплины через «действие и результат»: экран онбординга — это «заставить незнакомца доверить данные и дойти до ценности» → поведенческая экономика (friction, default effect), копирайтинг (микротексты несут половину конверсии), аналитика продукта, доступность.

**П.3 — основания.** Первичное: аналитика по шагам, записи сессий, текущие макеты и дизайн-система, тикеты поддержки по этому флоу, ограничения платформы. Выжимка «пользователи жалуются на сложность» недостаточна — нужны конкретные жалобы. Инструменты воркера: доступ к дизайн-системе (токены, компоненты), среда для кликабельного прототипа, аналитика.

**П.4 — проверка.** Критерии измеряют цель: завершение шага, время до ценности, число обращений в поддержку — а не «красиво» и не «соответствует гайдлайнам» (это требование, не критерий). Независимая проверка: тест с 5 людьми из аудитории по сценарию; эвристический аудит другим агентом по чек-листу; сравнение с текущей версией на одном задании. Тест на опровержение: человек из целевой аудитории с задачей и без подсказок — доходит ли до конца.

## Ловушки

- **Подмена цели эстетикой.** «Современнее» и «чище» — не критерии. Если нет цели за экраном, п.1 должен её найти или честно сказать, что задача декоративная.
- **Роль вместо метода.** «Подумай как UX-исследователь» ничего не даёт. Метод — «проведи 5 коридорных тестов с протоколом», «сверь с WCAG 2.2 AA по чек-листу».
- **Редизайн всего.** Амбиция ≠ объём. Один убранный шаг ценнее трёх перерисованных.
- **Проверка на себе.** Автор макета — худший испытуемый. Верификатор должен получить сценарий задания и прототип, не объяснение дизайнера.

## Для воркера

- Начни с входной проверки, если она есть: данные воронки или сессии — до первого пикселя.
- Каждое решение в макете — к какой проблеме из проверки оно относится. Решение без проблемы — кандидат на удаление.
- Дизайн-система: используй существующие компоненты; новый компонент — с обоснованием, почему существующих недостаточно.
- Состояния: пустое, загрузка, ошибка, предельные значения, длинные строки, маленький экран. Макет без состояний — не готов.
- Доступность: контраст, фокус, порядок табуляции, размеры целей — проверь инструментом, не глазом.
- Передавай: макет или прототип; карту «проблема → решение»; сценарий для тестирования, по которому верификатор сможет проверить без тебя.

## Пример двух планок

Задача: «Переделать экран ввода данных компании в онбординге B2B».

- Базовая: экран по текущей дизайн-системе, все состояния, доступность, сценарий для теста.
- Амбициозная: выяснить, какие поля можно заполнить автоматически по ИНН или домену, и убрать их с экрана; проверка — какая доля полей в текущих заявках совпадает с данными из открытых реестров (материал: 50 последних заявок, предел — 2 часа, критерий — ≥40% полей автозаполняемы).
